Security model

A tool that demonstrates credential theft has to survive the question "what if it is pointed at me?". v1 did not; v2 was rebuilt around the answer, and the test suite pins each control closed.

Where the boundary sits

Anyone who can read the dashboard page — loopback, same origin — is the operator. That is the design: the console answers to the token, and the token is a lock on the door, not on the room.

Against a hostile web page, the boundary is airtight, and each layer is independent:

It can reach the port

But a cross-origin fetch() cannot read the response — same-origin policy.

It cannot set the header

The custom X-Signal-Token header forces a CORS preflight, which is never approved, so the request is never sent. This is what protects state-changing routes from CSRF.

It cannot guess the token

256 bits from crypto/rand, regenerated per run, compared in constant time.

Rebinding gets nothing

A rebinding page reaches the port with its own hostname in Host, which is refused before any handler runs.

Two limits, documented rather than hidden

1. The token defends against remote pages, not against local processes. GET / serves the dashboard with the token inside it, and that route is guarded only by the loopback Host check. Any process that can reach loopback — including one running as a different local user, since loopback is machine-scoped — can read the token and then use POST /v1/sys/cmd to execute commands as the user running the console. The practical consequence is a deployment rule: run the console on a single-user workstation. On a shared or RDP host it is a cross-user escalation path.
2. POST /v1/sys/opt changes the machine with no flag. It writes HKLM policy and stops + disables the DiagTrack service, and unlike every other state-changing capability it requires only the token — there is no --enable-* gate, because the action is privacy hardening rather than credential access. It is listed on the Capabilities page so nobody discovers it by accident.

Both are written into the repository's SECURITY.md under "Documented limits" rather than left to be discovered by whoever reads the code next. The discussion, the trade-offs and the rejected options live in issue #6, which is closed.

Intentional capabilities

These are features, not bugs — they are the reason the tool exists:

  • POST /v1/sys/cmd executes shell commands as the token holder.
  • --enable-collect decrypts browser credential stores and the local SAM/SYSTEM hives on the local host.
  • --enable-inject performs W^X process injection into an operator-selected local PID.
  • --enable-persist creates and removes local persistence footholds.
  • --enable-lateral executes commands on operator-supplied remote hosts over WinRM or SCM.
  • --enable-evasion neuters ETW/AMSI in this process only.

They are reachable only over loopback, only with the per-run token, and the credential, persistence, evasion, lateral and injection modules additionally require their flag at startup. Hardening regressions in that chain are in scope for vulnerability reports.

Out of scope

Physical access, kernel-level attackers, and the operator console itself once the token holder is trusted. Reports about the intentional capabilities above are answered with a pointer to this page unless they show the gate failing — a route reachable without its flag, a non-loopback bind, a missing Host or Origin check, a token comparison that leaks, or a state-changing route that a hostile page can reach.

Reporting a vulnerability

Report privately, never in a public issue with exploit details: GitHub → Security → Report a vulnerability on DevCop95/pullgoscript, or open a minimal issue titled [SECURITY] asking for a private channel. Include the affected version or commit, impact, reproduction steps and any suggested fix. Expect an acknowledgement within 72 hours and a status update within 10 business days; fixes are credited in the release notes unless you prefer otherwise. The full policy is in SECURITY.md.
